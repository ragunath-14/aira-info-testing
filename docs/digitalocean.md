# DigitalOcean

## Token scoping

The console uses two tokens and treats the split as a security boundary.

```env
DIGITALOCEAN_API_TOKEN=dop_v1_...        # read scope
DIGITALOCEAN_WRITE_API_TOKEN=dop_v1_...  # write scope, power actions only
```

Create both under **API → Tokens** with custom scopes:

| Token | Scopes |
| --- | --- |
| Read | `droplet:read`, `block_storage:read`, `firewall:read`, `image:read`, `snapshot:read`, `reserved_ip:read`, `monitoring:read`, `database:read`, `account:read` |
| Write | `droplet:update`, `droplet:create` (snapshots), `snapshot:create` |

**Omit the write token to run a genuinely read-only console.** Droplet actions are
then refused with an explanation, not silently downgraded to the read token — the
refusal is in `providers/digitalocean/client.ts` → `write()`.

Never grant `droplet:delete`. The console has no operation that deletes a droplet,
so the scope would only widen the blast radius of a stolen token.

## Environment tagging

Environment drives every guardrail, so tagging is not cosmetic.

Tag each droplet with one of `env:development`, `env:testing`, `env:staging`,
`env:production`. Bare tags (`production`) and common shorthands (`prod`, `stg`,
`qa`, `dev`) are also recognised, case-insensitively.

```bash
doctl compute droplet tag prod-droplet-01 --tag-name env:production
```

**An untagged droplet is treated as production.** That is deliberate: an unlabelled
resource inherits the strictest guardrails rather than the loosest. The visible cost
is that an untagged development box appears as production until it is tagged; the
alternative cost is a production box treated as development, which is how accidents
happen.

Resolution lives in `providers/digitalocean/mapper.ts` → `environmentFromTags()` and
is covered by unit tests.

## What the console reads

| Endpoint | Used for |
| --- | --- |
| `/droplets` | Inventory, paginated to a 10-page cap |
| `/droplets/{id}` | Detail view (the list response omits backup ids on some plans) |
| `/droplets/{id}/snapshots` | Snapshot list and the most recent backup timestamp |
| `/volumes` | Attached block storage |
| `/firewalls` | Inbound and outbound rules |
| `/snapshots` | Account-wide snapshots |
| `/floating_ips` | Reserved addresses and their assignment |
| `/monitoring/metrics/droplet/*` | CPU, memory, filesystem, load, bandwidth |
| `/databases` | Managed cluster backup state |
| `/account` | Cheap authenticated call used by the health check |
| `/actions/{id}` | Following an action to completion |

There is no passthrough endpoint. Every call is a named method in `client.ts`, so
the browser cannot reach an arbitrary DigitalOcean path.

## Metrics caveats

CPU and bandwidth come from the hypervisor and are always available. **Memory,
filesystem and load require the DigitalOcean monitoring agent on the droplet.**

Without the agent, those metrics land in the response's `unavailable` list and the
UI shows *"Requires the DigitalOcean monitoring agent on the droplet"* — not `0%`.
An unmonitored droplet must never look like a healthy one.

```bash
curl -sSL https://repos.insights.digitalocean.com/install.sh | sudo bash
```

CPU is reported as cumulative per-mode counters, so the console derives a busy
percentage from the delta between consecutive samples. Filesystem and memory are
reported as *free*, so used is computed as total minus free. Both conversions are in
`mapper.ts` with tests.

## Permitted actions

| Operation | Permission | Production | Confirmation |
| --- | --- | --- | --- |
| Reboot droplet | `digitalocean.reboot` | allowed | typed |
| Power on droplet | `digitalocean.power` | allowed | none |
| Power off droplet | `digitalocean.power` + `infra.manage` | **not available** | typed + second approval |
| Snapshot droplet | `digitalocean.snapshot` | allowed | none |

Hard power-off is unavailable in production for anyone — it is not a permission
question. Use a graceful reboot, or take the droplet out of rotation first.

Snapshot names are generated by the console (`<droplet>-console-<timestamp>`); the
name is never taken from the request.

Every action re-resolves the droplet first, so an id belonging to an environment the
operator cannot see returns 404 before any provider call is made.

## Rate limits

DigitalOcean allows 5,000 requests per hour. The console stays well inside that:

| Data | TTL |
| --- | --- |
| Droplet inventory | 45s |
| Volumes, firewalls, snapshots, floating IPs | 120s |
| Metrics | 20s per droplet per range |
| Managed database clusters | 120s |

A 429 is classified as retryable and surfaced with the provider's `Retry-After`. On
any failure the UI falls back to the last known good data and labels its age.

## Managed databases

Register a managed cluster as a database connection (Database → Connections). The
console matches it to a DigitalOcean cluster by host to report backup state.

Use `sslMode: verify-full` and a read-only database user — see
[setup.md](setup.md#give-the-console-its-own-database-user). With that in place,
production read-only is enforced by the console's policy *and* by PostgreSQL.

## Troubleshooting

**"DigitalOcean rejected the console's credentials"** — the token is revoked,
expired or lacks a scope. Rotate it, then restart the API so the client is rebuilt.

**Droplets missing from the list** — check the environment tag. Your role may not
cover the environment the droplet resolved to. An untagged droplet resolves to
production, which an intern or developer cannot see.

**Metrics show "not collected"** — the monitoring agent is not installed, or the
droplet was created too recently for a sample to exist.

**A reboot returns "no DigitalOcean write credentials"** — the console is
intentionally read-only. Set `DIGITALOCEAN_WRITE_API_TOKEN` if power actions are
wanted on this instance.
